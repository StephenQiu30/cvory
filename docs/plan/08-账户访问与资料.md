# 账户访问与资料

唯一来源 PRD：[PRD 08](../prd/08-账户访问与资料.md)。PLAN-CV-08。设计和验收的已确认／建议状态以来源为准，不自动授权公开部署。

## 1. 交付目标

让个人通过 GitHub 安全访问自己的私有工作区，维护账户资料，并以可验证的隔离与完整 schema 支持运行。

## 2. 执行步骤

首个实施切片（与 Plan 01 共用后端）：

- `backend/src/config/`、`common/`、`database/` 建立配置、Google 错误/会话 Guard、参数化 MySQL 事务边界；`backend/test/` 用隔离 MySQL 与真实 HTTP 验证。
- `modules/account/` 实现现有 scrypt/会话读取与显式兼容登录；`modules/github/` 实现 state/PKCE/浏览器绑定、一次性回调、数字 ID 映射和双身份绑定，公开仓库仅读取本人公开素材。
- `modules/cvs/` 延续 JSON/etag/所有权，保存事务形成历史并恢复为副本；单一 schema 补齐结构时不重置现有 CV owner 或公开地址。
- 先写失败测试并观察，再实现；覆盖跨账户、冲突、恶意正文、无邮箱、重放/账号绑定冲突、历史恢复。OAuth 外部网络使用隔离模拟器，真实 GitHub 单独验收。
- 生成新增身份接口客户端，前端提供 GitHub 入口及未配置反馈，保留存量邮箱入口。通过后更新 README/PROJECT/HANDOVER，仍不自动替换运行中的旧服务。


1. 对照 NestJS 账户、会话、限流及前端弹窗与 PRD 的 AC，用兼容数据及 Git 历史核对存量合同和缺口；确认公网目标、代理信任、认证策略与负载门槛。
2. 在隔离 MySQL 盘点 schema、归属、邮箱唯一性及 legacy，准备完整 schema、备份及失败恢复；先兼容后回填，收紧约束前验证数据，不自动认领 legacy。
3. 以服务端会话为唯一 owner 来源，逐一核对账户、CV、照片、预设、候选、PDF、发布与缓存；实现缺失的跨账户隔离和不同账户重新登录时的草稿保护。
4. 落实 NestJS GitHub OAuth 授权码、state、PKCE、数字 ID 身份映射与本站会话；明确 GitHub-only 账户可空邮箱/密码，保护存量兼容与双身份绑定，补充来源/CSRF、可信代理、Cookie、会话有效期与撤销、分维限流和脱敏日志；同步 OpenAPI、生成客户端与调用方。
5. 按设计完善资料和手机／桌面弹窗的键盘、状态与错误反馈；保存失败和认证失效不清除用户输入。
6. 在隔离环境执行 PRD 的账户、隔离、限流并发、会话和迁移场景；执行 NestJS 工程届时登记的类型检查、lint、单元/集成测试与构建，以及现有前端 lint/build 和隔离浏览器检查；脚本未建立时不虚构命令或通过记录。真实 MySQL 和目标 HTTPS 环境单独验证。

7. 将历史、本机恢复、打印票据及执行器绑定纳入两账户隔离矩阵，保留重新认证前的输入。

8. 在模拟 OAuth 中验证取消/重复回调/ID 不变而 login 改名/无邮箱/同邮箱冲突；原账户与 GitHub 双方核验后绑定，不能按邮箱直接合并。
9. 接入本人公开仓库分页、选择和同步时间/失败反馈，来源元数据与人工成果分开；项目纳入简历或发布都需明确确认，不抓源码、不读私库。真实 GitHub 在后续配置完成后独立验收。

移除旧运行时：迁移资料/图片、将当前完整数据库结构收敛到唯一 schema.sql，并提供显式、保留数据的结构应用命令；统一 OpenAPI/生成客户端、Docker/Compose 与前端默认地址。旧密码修改保持验证/撤销其他会话；邮箱恢复和注销未完成时关闭入口。清理 Python 源码、旧测试/清单和锁文件后，在真实 MySQL/浏览器与容器构建验证，合并 main 并核对推送结果。
