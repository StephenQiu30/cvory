# 文档管理与 Obsidian 设计

依据：[PROJECT](../../PROJECT.md#35-文档工作区)。本文是文档治理设计，不属于产品业务需求，也不派生产品 PRD。

## 1. 目录与所有权

| 位置 | 只维护什么 |
| --- | --- |
| requirement | 业务原始诉求与核心需求说明 |
| design | 方案、数据关系与必要技术取舍 |
| prd | 可独立交付能力的范围与验收 |
| plan | 对应能力的实施步骤与验证 |
| research | 正式调研结论、来源和局限 |
| templates / assets | 简短模板、会继续使用的最终附件 |
| 根 PROJECT / AGENTS / DESIGN | 工程与文档规则、协作流程、视觉交互 |
| 根 BACKLOG / HANDOVER | 唯一调度入口、最近交付证据 |

一项完整需求只对应一份产品 design。一个 design 可有多个 PRD，一个 PRD 可有多个 Plan；下游直接来源唯一，显式链接登记。按用户结果拆分，不按每个按钮、技术层或检查动作建文档。

## 2. 精简原则

业务说明不记录文档整理过程、技术清单或代理规则。补充业务并入原需求，规则修改回对应根规范，不为每次会话新增需求文件。

中间稿、过程确认、提示词、原始工具输出、临时截图、重复摘要和未采用素材不写入项目。必要结论并入正式正文，不建立额外归档目录保留这些内容。既有历史通过 Git 查询。

正文只维护自己的信息，其他位置引用。状态只在 BACKLOG，证据只在 HANDOVER。技术、验收和步骤变化分别修改对应 design、PRD、Plan，原始诉求保留不改写。

## 3. 阅读与维护

从[文档中心](../00-文档导航.md)沿需求 → design → 对应 PRD → Plan 阅读。docs 是 Obsidian vault，不是网站；通用配置入库，个人配置与缓存不入库。相对链接和核心功能的用法见[Obsidian 说明](../01-Obsidian使用说明.md)。

各目录以 00 导航为入口，编号与路径使用 PROJECT 的规则。变更后检查来源、相对链接、锚点、编号及内容覆盖；临时检查不落项目文件。
