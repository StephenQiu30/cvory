# 文档管理与 Obsidian 设计

状态：已确认。依据：负责人要求在 CV 仓库按 lucky 的文档目录、模板和 Obsidian 用法初始化知识库。本文只确认文档工作方式。产品范围、技术选型和实施排期仍待定。

方法来自 lucky 仓库的 `docs` 体系：根导航、`design → prd → plan`、`requirement` 来源保护、三份写作模板，以及 Obsidian 核心插件配置。lucky 的产品正文、验收编号、服务边界和实施状态留在 lucky，不复制到本库。

## 1. 目标与范围

`docs` 保存原始需求、设计、PRD、Plan、调研、模板和附件。Obsidian 提供本地搜索、反向链接、图谱、提纲和布局。文档目录不包含网站、脚本、测试、依赖、锁文件或生成页，不参与应用构建。

[仓库说明](../../README.md)指向本库。根规范已有 [PROJECT](../../PROJECT.md)、[AGENTS](../../AGENTS.md)、[BACKLOG](../../BACKLOG.md) 和 [HANDOVER](../../HANDOVER.md)。工程代码还没有。

## 3. 导航与编号

根入口为 [00-文档导航.md](../00-文档导航.md)。子目录入口为各自的 `00` 导航。现行文档使用 `NN-中文名.md`，新增取该目录下一编号。重编时同步路径、正文编号、导航和来源映射，不保留重复文档。

原始需求入库后，正文、文件名、原编号和业务 ID 保持原样，不能按设计编号重排。导航和来源说明写在原文之外。

各目录独立编号。PRD 链接唯一来源 design，Plan 链接唯一来源 PRD。相同文件号不表示父子关系。

## 4. Obsidian

打开 `docs` 作为 vault。使用相对 Markdown 链接、核心搜索、反向链接、图谱、提纲、模板和 Workspaces，无社区插件。通用 `.obsidian` 配置入 Git。个人 workspace、graph、书签、快捷键、插件缓存和回收站不入 Git。自动链接更新关闭，避免重命名时改写原始资料。

附件放入 `assets`，在正文里引用原文件。根规范和工程 README 用仓库相对链接引用，不复制进 vault。

## 5. 新增一篇文档

1. 从来源或负责人确认里摘出已确认、建议、待定。
2. 用 [设计模板](../templates/01-设计模板.md) 写技术合同，登记到 [设计导航](00-设计导航.md)。
3. 需要给人评审范围时，另写一份 PRD，链接这份 design，并登记到 [PRD 导航](../prd/00-PRD导航.md)。
4. 需要交给执行时，按 PRD 拆 Plan，每份 Plan 链接唯一 PRD，并登记到 [Plan 导航](../plan/00-Plan导航.md)。
5. 用户故事和测试场景使用对应模板，放进所属设计或 PRD，不单独开产品目录。
6. 顺序、优先级、阻塞和状态只写在 [BACKLOG](../../BACKLOG.md)。

## 6. 检查

变更后核对编号、相对链接、锚点、路径大小写和事实。来源正文入库后按入库时的文件比对，不自动改写。客户端里的布局和图谱另作验收，JSON 可解析不等于 Obsidian 已经打开通过。
